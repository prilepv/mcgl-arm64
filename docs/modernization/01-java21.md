# Milestone 1 — Java 21 ARM64

## Reference baseline: 1.6.7

Reference tag: `v1.6.7` (`efd8498e6a7019b208923d4b678d484e2ff96f34`).
The later documentation/privacy commits are retained. Before migration, runtime,
launcher, patches and tests matched that release. The discarded `1.6.7-hotpaths-1` experiment is not
included. The installed user profile still contains that experiment and is NOT
a valid baseline for these tests. Validation uses new isolated directories.

This milestone changes Java only. LWJGL 2, its Cocoa window/input integration,
legacy OpenGL 2.1, existing rendering/performance patches, gameplay and protocol
must remain unchanged. No release publication is authorized by this milestone.

## Status

**PASS — Java 21 controlled migration**, with the coverage and remaining risks
below. Version: **1.6.7 → 1.6.8 (local candidate, not published)**.
Java 21 build/tests, real-server gameplay, rendering/input/sound, existing
window/fullscreen behavior and ordinary network shutdown passed. No LWJGL 3,
GLFW, Core OpenGL or renderer modernization was started. No tag, commit,
release upload or installed-application replacement was performed.

## Baseline build/runtime

- Zulu OpenJDK `1.8.0_502-b07`, Zulu `8.96.0.19`, `aarch64` / Mach-O ARM64.
- Java source/target 8; original client and dependency class files remain older.
- Shell build recipes, Ant 1.10.15 for LWJGL native, Apple Swift 6.1.2 (Swift 5

- JVM is embedded using `dlopen` / `JNI_CreateJavaVM`, not a shell `java` command.
  Cocoa/OpenGL preflight and the AppKit event loop own the first macOS thread;
  the existing dedicated attached Java thread runs DirectLauncher/game logic.
- Bootstrap classpath: `mcgl-nativewindow-patch.jar:Minecraft.jar` relative to
  the game directory. The official MCGLClassLoader explicitly creates its own
  URLClassLoader for LWJGL, JInput, lwjgl_util, HTTPClient/Core, commons-logging,
  Gson and the patched `bin/mcgl.jar`.
- Baseline Java 8 paths are `java8-arm64/Home`,
  `Home/jre/lib/server/libjvm.dylib`, and `Home/bin/{java,jar}`.
- Existing heap/FPS/GC/VBO/diagnostic environment settings are retained.
- App bundle is signed ad-hoc; release recipe builds ZIP and a separate tool
  creates DMG. Neither is Developer ID signed or Apple notarized.
- Existing prepared-input production build passed; packaging audit reported
  67 ARM64 Mach-O files, deployment <= macOS 14, valid ad-hoc signature.
  This does not mean a dependency-free clean-checkout build is now supported.

## Java 21 implementation

Selected runtime: Azul Zulu **21.0.12.1+1-LTS**, Zulu **21.52+203-CA**, macOS
ARM64, normal GA/CA JDK. The 205,924,000-byte vendor archive was verified
against Azul's SHA-256 (recorded in `docs/DEPENDENCIES.md`). An earlier Oracle
21.0.10/aarch64 probe was diagnostic only and is not redistributed.

The runtime is now `java21-arm64/Home`, with `lib/server/libjvm.dylib` directly
under Home. The launcher installer still uses bundled `bin/java` and `bin/jar`.
The complete modular JDK is bundled with its legal notices: no guessed minimal
module set, `tools.jar`, host-Java dependency or symlink to a system JDK.

Only these additional module permissions are enabled:

```
--add-opens=java.desktop/java.awt=ALL-UNNAMED
--add-exports=java.desktop/com.apple.eawt=ALL-UNNAMED
--add-exports=java.desktop/com.sun.media.sound=ALL-UNNAMED
```

They cover the existing peerless Applet flag workaround, existing foreground
request, and LWJGL 2's legacy URL WAV reader respectively. No blanket opens,
`--illegal-access`, custom system classloader or SecurityManager override.
The JavaVMOption array has an explicit bounds check. JNI_VERSION_1_8 is retained
as the supported invocation ABI, not as a request to run Java 8.

G1 options and heap defaults are unchanged. The non-G1 branch now explicitly
uses `-XX:+UseParallelGC`, preserving the Java 8 choice instead of inheriting
Java 21's different default. New Java compilation uses `--release 8`; source
syntax, ASM 4 visitors, original client bytecode and gameplay logic are not
modernized. Baseline verification still supports JDK 8's source/target options.

## Compatibility findings and resolutions

- Java 21 has a modular runtime layout, without the old nested `jre` or
  `tools.jar`; native lookup, launcher validation and packaging need adaptation.
- DirectLauncher reflects over `GraphicsEnvironment.headless/defaultHeadless`.
  Java 21 strong encapsulation requires a narrowly scoped `--add-opens` for this
  deliberate existing Applet workaround. Applet remains in 21, deprecated for
  removal; this milestone does not replace it with GLFW/AWT windows.
- G1 is the newer JDK default; the disabled-G1 launcher setting must explicitly
  retain ParallelGC rather than silently changing collectors on migration.
- Java 8 and selected Java 21 both report UTF-8 on this Mac. A new executable
  test confirms default charset, a Cyrillic path and WAV decoding on both.
  Password transport already specifies UTF-8; no protocol encoding is changed.
- Existing ASM 4.0_RC1 visitors/patchers must not be upgraded casually. Keeping
  helper/overlay class files at Java 8 compatibility avoids unnecessary new
  bytecode constructs; the original Java 21 compiler/test trial already passed.
- LWJGL MemoryUtil references removed `sun.reflect.FieldAccessor`, but tries
  `sun.misc.Unsafe` first, then fallbacks; a static warning alone is not proof
  that the selected runtime path is broken.
- `WaveData.create(URL)` failed with **IllegalAccessError** on Java 21 in the
  new focused test. Exporting only `java.desktop/com.sun.media.sound` fixes
  the existing implementation; the library was not replaced. This was a real
  compatibility failure even though menu OpenAL initialization already worked.
- The main MCGLClassLoader constructs its own URLClassLoader and does not cast
  the system loader. Original client `ClassLoader.sys_paths` mutation no longer
  finds its private field; the existing catch handles it. Explicit JNI/LWJGL/
  JInput paths supply the correct libraries, verified in the live process.
- The client's rare `ClassLoader.loadedLibraryNames` diagnostic also references
  a removed private field. Its existing catch skips that report on Java 21.
  No validation/protocol code was patched or deliberately bypassed. Initial
  real-server acceptance is confirmed, but all rare reporting paths are not.
- Optional Discord RPC uses a system-URLClassLoader cast, invalid on Java 21.
  Its setting defaults off; enabling it is not certified. The supplied Discord
  native is x86_64 and bundled JNA native is i386/x86_64, so this dependency was
  not an operational ARM64 feature in the Java 8 baseline either. No unrelated
  Discord/JNA upgrade or feature switch was introduced.
- Two `Thread.stop()` calls remain in the client's five-second network watchdog.
  Java 21 throws UnsupportedOperationException; the existing catch swallows it.
  Normal shutdown already clears the running flag, closes data streams/socket
  and has an interrupt path. No speculative networking rewrite was made.
  Live normal disconnect passed: both Client read/write threads were present
  while connected and absent after returning to the galaxy menu; no network
  watchdog thread remained. The rare emergency fallback remains a known Java
  21 limitation, not a claim of complete disconnect/timeout coverage.
- No newly required removed JDK module or custom SecurityManager installation
  was found in the startup path. Existing privileged calls and optional native
  cleanup/finalizer patterns remain; finalization has not been disabled and no
  new lifecycle/thread model was introduced. Long-session cleanup is a risk
  requiring soak testing, not covered by short algorithm tests.
- Native library loading, AppKit first-thread ownership, attached Java game
  thread, relative classpath, explicit game cwd and environment-based settings
  are preserved. The native OpenGL context is still the **legacy** profile.

## Automated validation

The unchanged `verify-source.sh` completed on both Java 8 and Java 21 with
original client JAR inputs: 44 test-process invocations each, 0 failed, no
original-client tests skipped. PASS markers are not counted as separate tests;
some processes emit multiple markers. This is not a count of individual asserts.

Breakdown per original suite: **20 Swift processes + 24 Java processes = 44**.
Swift: UI, account layout, 11 image checks, updater, two upgrade-fixture checks,
preferences, accounts, password storage and installer migration. Java: three
base tests, eight diagnostic combinations, four texture-binding combinations,
nine original-JAR tests. The patch-generation command is a pipeline action,
not an extra test count.

The final extended suite on both Zulu 8 and Zulu 21 reports **46 PASS / 0 FAIL**
per run: the original 44 test-process cases plus two new compatibility processes
(G1 and ParallelGC). Original client JARs and accompanying lwjgl_util were
provided; none of these checks were skipped. This is **not** a count of asserts.

The untouched 44-case suite was run before changing any version expectations.
After successful runtime validation, release metadata was promoted to 1.6.8.
The historical 1.6.7 updater fixture still has the same response and must offer
an update to 1.6.5/1.6.6, but not to 1.6.7 **or 1.6.8**. Its accepted-current
version matrix was expanded for that metadata bump, and explicit forward/
backward 1.6.7↔1.6.8 comparisons were added. No game/algorithm expected output
was weakened or changed to hide a failure. The final 1.6.8 suite was rerun:
**46 PASS / 0 FAIL**, plus the existing optional UI forms process **1 PASS /
0 FAIL**. Final automated total: **47 test-process invocations, 47 PASS, 0 FAIL**.

The optional existing UI `--forms` process also passes when run outside the
sandbox. Its initial sandbox failure to open an AppKit sheet is retained as an
infrastructure failure, not relabeled PASS. Two integration attempts for the
new compatibility test failed because Bash 3 treats an empty array as unbound
under `set -u`, and a loose overlay class conflicted with the sealed LWJGL JAR.
The harness now uses a nonempty argument array and a separate compatibility
class directory. Neither fix changes expected behavior or library sealing.

The local isolated UI helper initially crashed from using its own bundle ID
as a UserDefaults suite. A separate suite fixes it; this was not a Java/client
crash. The helper and its private profiles remain outside the repository.

- Java 8 baseline and Oracle 21 diagnostic probe each rendered the actual menu
  for 60 seconds with the same patched client and LWJGL stack. Both ended via
  the harness's planned timeout/termination (143), not a claimed clean exit.
- The self-contained Zulu 21 candidate launched through the Swift launcher and
  NSWorkspace into an isolated profile, fetched/verified official client updates,
  applied the unchanged port patch chain and entered the real target server.
  The downloaded official file manifest matches the locally supplied original.
- User explicitly confirms walking, mouse look, audible sound and real server
  entry. Visual inspection confirms world geometry/textures, HUD and minimap.
  No gameplay packets, server checks, terrain renderer or input APIs were patched.
- `jcmd VM.version` on the real game PID reports **21.0.12.1+1-LTS**. `lsof`
  confirms bundled libjvm/libjawt, isolated profile cwd and the port's LWJGL,
  JInput, OpenAL, nixspecific and valuelib libraries. No system Java symlink.
- Existing 1x Retina policy is logged, matching the baseline. User confirms
  inventory opening, live resize, fullscreen entry/exit. Resized 1255×700
  content and correct menu layout are also visually observed. Torches/world
  textures and chunk geometry render; entity-/particle-heavy scenarios were
  not separately exercised and are not claimed as exhaustive coverage.
- Before disconnect, jcmd captured Client read/write threads in normal socket
  read and timed sleep states. After the ordinary in-game exit-to-galaxy action,
  both and the network watchdog were absent and the menu remained responsive.
- Normal game exit logged `Stopping!`, SoundSystem shutdown and launcher
  process termination. No new game crash was observed. NSWorkspace does not
  report an exact numeric child exit status to this launcher; it is not invented.
- A separate final 1.6.8 menu-only run again loaded bundled Zulu 21, OpenAL and
  legacy OpenGL. Coordinate-based automation could not reliably close that

  No test game processes remained at handoff.
- The installed application, primary game profile and saved credentials were
  not replaced/read/copied. The first isolated GUI appended technical output to
  the normal launcher log; support-root injection now also isolates log output

## Performance sanity, not optimization

- User reports **25–40 FPS at maximum graphics settings**, and approximately
  the same on Java 8. This is a user-observed comparison, not a controlled A/B.
- Baseline/probe warmed animated menus were ~35 FPS, ~28 ms average frame;
  first initialization-containing frames ~3.48 s on 8 and ~3.58 s on Oracle 21.
  These are menu observations, not world FPS or full launch-latency benchmarks.
- Selected Zulu 21 world logs show typical ~27–37 FPS / ~27–37 ms frames across
  the observed moving scene; outliers and window transitions are not optimized.
- Live sample: ~1.10 GiB process RSS, ~40.6% CPU; G1 heap 512 MiB committed,
  ~266 MiB used, maximum 2 GiB, Xms 512 MiB. A later RSS sample was ~1.25 GiB.
  Single samples do not establish a memory regression or a leak.
- jcmd confirms G1 and the existing 35 ms pause target/StringDedup options.
  jstat could not map this embedded JVM's perf-data context; heap/flags remain
  observable via jcmd. No GC tuning, CPU optimization or new threads were added.

## Remaining risks / regression policy

Do not call short successful gameplay a complete soak test. Unusual disconnects,
private native-library reporting, optional Discord integration, other macOS/Mac
hardware, long sessions and all possible resource packs remain unverified.
No new visual/performance regression has been demonstrated in the tested scene.
Any failed window or normal networking check must change the milestone outcome,
not be hidden behind passing headless tests.

The user requests native macOS fullscreen with Spaces/trackpad-desktop switching,
instead of the existing legacy fullscreen behavior. The same limitation existed
on Java 8 and is not a Java 21 regression. It requires a separately validated
Cocoa window/fullscreen change; it has deliberately **not** been mixed into this
milestone, and no new task/automation was created without an explicit request.
