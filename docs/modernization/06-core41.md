# Milestone 6 — OpenGL 4.1 Core context foundation / 1.6.13

## Status and scope

**CORE FOUNDATION VALIDATED IN THE 1.6.15 CHECKPOINT — 2026-09-08.**
Starts from verified [1.6.12](05-render-architecture.md).
Originally implemented without compilation or runtime tests at the user's
request. The later [milestone 8 checkpoint](08-indexed-geometry.md) compiled the
combined sources and verified actual Core profile/flags, GPU drawing,
resize/presentation, ownership and two context lifetimes in a local 1.6.15 APP.
No standalone 1.6.13 package was produced. Full game conversion is still pending.

This milestone supplies an explicit Core context/backend path, not a claim that
the existing fixed-function game has become Core-compatible. The normal game
entry point remains compatibility OpenGL 2.1 until the shader and geometry
migrations are integrated. No hidden fallback or per-frame profile switching
is introduced.

## Implementation

- `RenderProfile` separates compatibility 2.1 from Core 4.1. `RenderDevice`
  selects a backend through a profile-aware factory while retaining its
  historical compatibility factory overload. One device still owns the
  current context, thread guard and generation registry for both profiles.
  A live context generation cannot be reinterpreted as another profile.
- `ContextRequest.core41` requests version 4.1, Core profile and forward
  compatibility. RGB10 hints, sample/depth/stencil settings and 1:1 framebuffer
  scaling remain. GLFW verifies the returned version/profile attributes and
  rejects mismatches; there is no retry with legacy hints.
- `Core41Backend` creates LWJGL capabilities for the bound native context and
  requires actual OpenGL 4.1 support, the Core profile mask, absence of the
  compatibility bit and the forward-compatible flag. It records the queried
  version, driver and GLSL strings. A context that fails these checks follows
  the existing attachment-failure cleanup path.
- `FrameCommands` supplies viewport, clear color and buffer clear through
  core-safe `GL11C` bindings. Cached operations enforce context ownership,
  attachment and generation lifetime. Frame counters, window presentation,
  input, fullscreen and native CGL locking use the existing lifecycle.
- The Core backend exposes no `LegacyRenderCommands`. Attempting to use the
  old graphics adapters in that context fails before native drawing with a
  message that shader/geometry migration is required. No stub shaders,
  display-list emulation or guessed legacy feature flags are supplied.
- `MCGLCoreDisplay` is the explicit staged-renderer entry point. It shares the
  existing `Display` window/input lifecycle without changing that class's
  public legacy ABI. The existing `GLContext` overload retains the registered
  profile during detach/reattach; the public compatibility API remains.

The native pre-JVM Cocoa pixel-format preflight is still the existing legacy
bootstrap preflight; it does not certify a Core context. The actual Core
request occurs at GLFW window creation, and native binding checks run on the
render owner after the context is made current.

## Entry point for the next renderer milestones

The following is source-level usage, **not a tested runtime example**:

```java
MCGLCoreDisplay.create(new PixelFormat());
try {
    FrameCommands frame = RenderSystem.frameCommands();
    frame.viewport(0, 0, Display.getWidth(), Display.getHeight());
    frame.clearColor(0, 0, 0, 1);
    frame.clear(true, true, false);
    Display.update();
} finally {
    Display.shutdown();
}
```

The caller must use the existing macOS bootstrap/main-thread dispatcher and
render-owner setup. This is not a replacement for the game's render loop or
a launcher setting that makes legacy rendering work in Core. Mesh submission,
shaders, textures/material state and the final game entry-point switch belong
to the following renderer milestones.

## Versioning and changed areas

Source version 1.6.13 / internal build 173. Installer marker:
`Minecraft Galaxy ARM64 bootstrap lwjgl3-core41-foundation-1`.
The `lwjgl3-` prefix preserves existing alphaSort preferences. The renderer
manifest and existing client bytecode transformation are unchanged. The merged
library manifest declares both available source paths, with compatibility
remaining the default.

New source files: `RenderProfile`, `FrameCommands`, `GuardedFrameCommands`,
`NativeFrameCommands`, `Core41Backend`, and `MCGLCoreDisplay`.
Updated integration: `RenderDevice`, `RenderContext`, `RenderSystem`,
`RenderBackend`, `RenderCapabilities`, `CompatibilityBackend`, `ContextRequest`,
`GlfwWindow`, `Display`, and `GLContext`.
Version/marker and documentation files are updated. The packaging audit knows
the additional components; the renderer-boundary audit keeps the original
compatibility-call inventory and separately constrains Core initialization and
frame calls. Version/installer fixtures cover the new version and marker.
These audit/test changes were subsequently executed in the milestone 8 checkpoint.

No dependency update, GLSL game pipeline, VBO/VAO/index-buffer migration, chunk
algorithm change, gameplay/network change, new production thread, main-profile
replacement or publication is included.

## Validation and remaining integration

The milestone 8 checkpoint covers the initial Core/shader/geometry foundation.
The remaining integration validation must cover full game paths and broader
window scenarios, including:

- Real Core 4.1 version/profile/flags and GLSL facts, with no silent fallback.
- GPU clear/readback, resize/fullscreen and two full context lifetimes.
- Failed initialization, foreign/detached commands, cached frame commands after
  destruction, same-profile reattachment and profile-change rejection.
- Rejection of fixed-function access before native GL, with no false-positive
  legacy capability assumptions in the new pipeline.
- Complete game rendering on Core only after the dependent shader/mesh work,
  followed by image comparison, server/input/audio checks and normal shutdown.

Measured foundation results are recorded in milestone 8 / 1.6.15; no complete
Core gameplay or FPS claim follows from them.

## Technical references

macOS requires forward-compatible Core contexts for modern OpenGL; GLFW's
[window guide](https://www.glfw.org/docs/3.3/window_guide.html) and
[platform conformance notes](https://www.glfw.org/docs/3.1/compat.html) describe
the required hints and 4.1 support. Khronos documents the removal of the
[fixed-function pipeline](https://wikis.khronos.org/opengl/Fixed_Function_Pipeline)
from Core profiles. These are API constraints, not evidence that this source
change has been tested on hardware.
